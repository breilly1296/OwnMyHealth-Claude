## 1. Mission / Vision

OwnMyHealth is a **privacy-first, HIPAA-compliant health biomarker tracking platform** with insurance document management, AI-powered educational guidance, provider-patient collaboration, and expense tracking. The product is built for patients managing chronic conditions (the README names osteoporosis as the original anchor use case).

Code-derived product statement (verbatim from repo):

```text
// Source: README.md:3
A privacy-first, HIPAA-compliant health biomarker tracking platform with insurance
document management. Built for patients managing chronic conditions like osteoporosis.
```

```text
// Source: CLAUDE.md "What This Is"
Privacy-first HIPAA-compliant health biomarker tracking platform with insurance
document management, AI-powered guidance, provider-patient collaboration, and
expense tracking. Focused on secure tracking of health metrics with Claude AI
educational insights, insurance cost analysis, and provider data sharing via
consent-based access control.
```

**One-sentence mission (code-derived)**: *Give patients ownership of their health data — biomarkers, insurance, and costs — in one encrypted, consent-governed record, with AI that educates rather than diagnoses.*

A crisp, board-approved mission **statement** beyond this code-derived description is `TBD (external: owner interview; resolve via product owner / founder)`.

## 2. Core Principles

Each principle below maps to a **repo rule that enforces it** — these are not aspirations, they are wired.

| # | Principle | Enforcing rule (file:line) |
|---|---|---|
| P1 | **Privacy-first / PHI encrypted at rest** | All 39 PHI fields across 14 models are AES-256-GCM encrypted via per-user keys; the canonical list is `PHI_FIELDS` (`backend/src/services/encryption.ts:476-562`). A schema↔PHI_FIELDS guard test prevents drift (`backend/src/services/phiFieldsCoverage.test.ts`). |
| P2 | **Consent-first sharing** | Provider access exists only via an explicit patient grant: a provider creates a `PENDING` request (`backend/src/routes/providerRoutes.ts:171`), and the patient must approve it (`backend/src/routes/patientRoutes.ts:180`). Sharing is *not* paywalled — it is a patient right on every tier (`backend/src/config/plans.ts:54-59`). |
| P3 | **User owns their data (export + delete)** | `dataExport` is `true` on every tier with the comment "HIPAA requires this regardless of plan" (`backend/src/config/plans.ts:60`); never gated. Account deletion + export live under `src/components/settings/`. |
| P4 | **AI is educational, never diagnostic** | Server-side disclaimer is force-appended to AI output unless the model already included one: `disclaimerToAppend(emittedText)` (`backend/src/controllers/aiChatController.ts:289`, helper `backend/src/utils/aiDisclaimer.ts`). |
| P5 | **Every PHI access is audited (7-yr retention)** | Audit rows on cross-user PHI reads, e.g. provider biomarker access logs `PHI_ACCESS` (`backend/src/routes/providerRoutes.ts:507`). Retention is **DB-enforced**: the `audit_logs_delete` RLS policy forbids deleting rows newer than 7 years (`backend/prisma/migrations/20260613_force_rls_and_audit_retention/migration.sql`). |
| P6 | **Defense-in-depth tenant isolation (RLS)** | `FORCE ROW LEVEL SECURITY` on all 19 RLS tables, plus a boot hard-exit `assertRLSForced()` / `assertNoBypassRLS()` (`backend/src/services/database.ts`). |

## 6. Provider Collaboration Strategy

**Model**: consent-based, read-only provider access to a patient's data, scoped by per-relationship permission flags. Providers cannot write patient data (the `canEditData` consent column is retained in schema/RLS for a future feature but no provider write route consumes it).

### 6a. Consent state machine

`ProviderPatient.status` (`backend/prisma/schema.prisma:578-584`): `PENDING → ACTIVE → {SUSPENDED, REVOKED, EXPIRED}`.

```
  Provider                         Patient
     │                                │
     │ POST /provider/patients/request│
     │  (patientEmail)                │
     ▼                                │
  ProviderPatient(status=PENDING)     │
  providerRoutes.ts:171               │
     │                                │
     │      patient sees request      │
     │ ◀──────────────────────────────│
     │                                │ POST /patient/providers/:id/approve
     │                                │  { canViewBiomarkers, canViewInsurance,
     │                                │    canViewHealthNeeds, consentDurationDays }
     │                                ▼
     │                  status=ACTIVE, consentGrantedAt, consentExpiresAt
     │                  patientRoutes.ts:180
     │                                │
     │ GET /provider/patients/:id/biomarkers   │ PATCH /patient/providers/:id/permissions
     │  resolveProviderAccess(tx, p, pt,       │  patientRoutes.ts:330 (blocked if expired)
     │   'canViewBiomarkers')                  │
     │  providerRoutes.ts:456                  │ POST /patient/providers/:id/revoke
     ▼                                         ▼  status=REVOKED  patientRoutes.ts:422
  scoped read (RLS + app check + audit)
```

### 6b. Permission flags (`ProviderPatient`, `schema.prisma:129-132`)

| Flag | Default | Provider read route gated on it | Enforced via |
|---|---|---|---|
| `canViewBiomarkers` | `true` | `GET /provider/patients/:id/biomarkers` | `resolveProviderAccess(tx, providerId, patientId, 'canViewBiomarkers')` (`providerRoutes.ts:456`) |
| `canViewHealthNeeds` | `true` | `GET /provider/patients/:id/health-needs` | `resolveProviderAccess(... 'canViewHealthNeeds')` (`providerRoutes.ts:539`) |
| `canViewInsurance` | `false` | `GET /provider/patients/:id/insurance` (added M3) | `resolveProviderAccess(... 'canViewInsurance')` (`providerRoutes.ts:611`) |
| `canEditData` | `false` | _(no write route; UI toggle removed)_ | DB column + RLS `has_provider_access(..,'edit')` retained for future use (`providerRoutes.ts:38-43`) |

Access is gated **three ways in depth**: the single `resolveProviderAccess` choke point (app-layer), PostgreSQL RLS `OR has_provider_access(...)` policy branches (DB backstop), and an audit row on every cross-user PHI read (`providerRoutes.ts:507`).

```ts
// Source: backend/src/routes/providerRoutes.ts:455-463
const { access, biomarkers } = await withRLSContext(providerId, async (tx) => {
  const access = await resolveProviderAccess(tx, providerId, patientId, 'canViewBiomarkers');
  if (!access.ok) return { access, biomarkers: [] };
  const rows = await tx.biomarker.findMany({
    where: { userId: patientId },
    orderBy: { measurementDate: 'desc' },
  });
  return { access, biomarkers: rows };
});
```

### 6c. Revocation

- **Patient revoke**: `POST /patient/providers/:id/revoke` sets `status=REVOKED` and writes a `CONSENT_REVOKED` audit row before the change (`patientRoutes.ts:452-471`).
- **Consent expiry**: time-based via `consentExpiresAt`; expired relationships are denied at the choke point and on permission edits (`patientRoutes.ts:369-376`).
- **Account-state coupling**: provider loses access the moment the patient's account is deactivated or locked (`providerRoutes.ts:348-365`).
- **Consent-column immutability** (L23): a BEFORE-UPDATE trigger `provider_patients_guard_consent()` restores the four consent columns unless the writer is the patient or admin (migration `20260615_provider_consent_immutable_audit_insert_check`).

> The provider-facing UI is **shipped** (`src/components/provider/CareTeamPage.tsx`, `MyPatientsPage.tsx`). The old "no provider UI" framing is obsolete. Cross-references: [`API_REFERENCE.md`](./API_REFERENCE.md), [`DATA_MODEL.md`](./DATA_MODEL.md).

## 6a. Lab Connection Strategy (Quest FHIR)

**Model**: SMART-on-FHIR (OAuth 2.0 authorization-code grant with PKCE/S256) standalone patient launch to sync lab results directly from Quest (and other FHIR-R4 providers). Gated behind the `questFhirIntegration` plan feature (PRO/TEAM only).

Patient (PRO/TEAM)                Backend (services/fhir/)            Quest FHIR
      │                                  │                               │
      │ connect (requirePlanFeature      │                               │
      │  'questFhirIntegration'          │                               │
      │  fhirRoutes.ts:34)               │                               │
      │ ────────────────────────────────▶ buildConnectRedirect          │
      │                                  │  PKCE verifier + state         │
      │                                  │  (smartAuth.ts:101)            │
      │ ◀─── authorize URL ──────────────│  endpoints via                 │
      │                                  │  /.well-known/smart-config     │
      │ ── authorize + login ───────────────────────────────────────────▶│
      │ ◀── redirect ?code=&state= ──────────────────────────────────────│
      │ ── GET /fhir/callback ──────────▶ handleOAuthCallback             │
      │                                  │  exchange code (smartAuth.ts:194)
      │                                  │  encrypt tokens per-user key    │
      │                                  │  upsert LabConnection           │
      │                                  │  (labSyncService.ts:144)        │
      │ ── POST /fhir/sync ─────────────▶ syncLabResults                  │

- **Routes**: `backend/src/routes/fhirRoutes.ts` → `backend/src/controllers/fhirController.ts`.
- **Services** (`backend/src/services/fhir/`, 7 files): `smartAuth.ts` (OAuth/PKCE), `labSyncService.ts` (connect/sync/disconnect), `loincMapper.ts` (LOINC→biomarker), `fhirClient.ts` (data client), `urlSafety.ts` (SSRF allowlist — blocks the cloud metadata endpoint `169.254.169.254`, `urlSafety.ts:39`), `types.ts`, `mockFhirServer.ts`.
- **Encrypted token storage** (`LabConnection`, `schema.prisma:755`): `accessTokenEncrypted` (required), `refreshTokenEncrypted?` — both in `PHI_FIELDS` (`encryption.ts:558-560`), encrypted with the per-user key (`labSyncService.ts:144-187`).
- **Idempotency**: imports dedupe on the stable external id `fhir:{provider}:{obs.id}` stored in `Biomarker.sourceFile` (plaintext by design so dedupe needs no decryption); re-sync of an already-imported observation is a no-op, so it never clobbers user edits.
- **Env vars** (`backend/src/config/index.ts:266-280`): `QUEST_FHIR_CLIENT_ID`, `QUEST_FHIR_CLIENT_SECRET`, `QUEST_FHIR_BASE_URL` (default `https://api.questdiagnostics.com/fhir/r4`), `QUEST_FHIR_REDIRECT_URI`, `QUEST_FHIR_SUCCESS_REDIRECT`, `QUEST_FHIR_AUTH_HOSTS` (SSRF allowlist). Feature is disabled unless `QUEST_FHIR_CLIENT_ID` is set.
- **Tier gate**: `requirePlanFeature('questFhirIntegration')` on connect + sync (`fhirRoutes.ts:34,59`); `false` on FREE, `true` on PRO/TEAM (`plans.ts:61,80,99`).
